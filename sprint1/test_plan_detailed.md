# Test Plan: Sprint 1

## 1. Основание для плана

План составлен по фактическому содержимому каталога `sprint1` на текущем этапе.

Сейчас в спринте есть:

- [README.md](/home/magesty_/Projects/python-ant-on-simulator/sprint1/README.md) с описанием предметной области и требований;
- [requirements.txt](/home/magesty_/Projects/python-ant-on-simulator/sprint1/requirements.txt) с набором инструментов;
- каркас тестов [tests/test_animal_ant.py](/home/magesty_/Projects/python-ant-on-simulator/sprint1/tests/test_animal_ant.py).

Сейчас в спринте нет:

- реализации модели колонии;
- реализации сохранений;
- реализации симуляции;
- реализации генерации муравейника.

Поэтому тест-план ограничен тем, что реально можно и нужно проверить в рамках первого инкремента.

## 2. Цель

Подготовить проверяемую основу для дальнейшей реализации спринта:

- проверить, что требования зафиксированы и не противоречат сами себе;
- проверить, что тестовая инфраструктура для `pytest` заведена;
- определить минимальный набор тестов, который должен появиться вместе с первой рабочей реализацией.

## 3. Scope

В scope этого плана входят:

1. Структура артефактов спринта.
2. Корректность и полнота требований в `README.md`.
3. Готовность окружения для написания автотестов.
4. Подготовка списка обязательных тестов на первую реализацию.

Вне scope:

- выполнение бизнес-сценариев, для которых еще нет кода;
- интеграционные проверки БД;
- проверка симуляции во времени;
- проверка комнат и карты муравейника на уровне runtime.

## 4. Основные риски текущего состояния

- требования описаны, но не декомпозированы в тестируемые сущности;
- в `README.md` есть опечатки и неоднозначные формулировки, которые потом дадут разные трактовки;
- тестовый каркас создан, но пока не проверяет ничего;
- команда может начать реализацию без фиксированного минимального набора acceptance checks.

## 6. Минимальный набор тестов, который должен появиться с первой реализацией

Ниже не текущие исполняемые тесты, а обязательный минимум на ближайшую реализацию.

### 6.1. Сохранения

- создание колонии с валидными входными данными;
- отказ в создании колонии при невалидных значениях;
- сохранение колонии в локальное хранилище;
- загрузка сохраненной колонии без потери полей.

### 6.2. Вид муравьев

- проверка, что `Messor structor` создается с параметрами из `README.md`;
- проверка, что в первом спринте доступна только роль рабочего.

### 6.3. Симуляция

- запуск симуляции двигает время вперед;
- пауза останавливает изменение состояния;
- один шаг симуляции меняет состояние ровно на один тик.

### 6.4. Муравейник

- при создании колонии автоматически создается стартовая карта;
- в структуре присутствуют обязательные помещения:
  - склад пищи;
  - мусорка/кладбище;
  - поверхность;
  - королевский зал.

## 7. Критерий готовности спринта к тестированию

Спринт можно считать готовым к полноценному тестированию, когда:

1. в `sprint1` появится код предметной логики;
2. для него будут созданы реальные `pytest`-тесты вместо заглушки;
3. спорные места из `README.md` будут уточнены или зафиксированы как принятые допущения.

## 8. Вывод

На текущем этапе `sprint1` находится в состоянии подготовки: требования и каркас есть, но тестировать бизнес-логику пока нечего. Поэтому основной смысл этого плана:

- зафиксировать, что уже можно проверить прямо сейчас;
- обозначить пробелы в требованиях;
- задать минимальный тестовый baseline для следующего шага реализации.
