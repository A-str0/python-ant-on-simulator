# Тест-план для QA: Sprint 1 — симулятор муравьиной колонии

## 1. Назначение документа

Этот документ предназначен для QA-инженера, который будет писать автотесты для первого спринта проекта «Муравьи».

Цель тест-плана — заранее зафиксировать, какие сценарии нужно проверить, какие граничные значения использовать и какие расхождения между требованиями и текущей реализацией считать багами или незакрытыми задачами.

## 2. Основание для тестирования

Основные источники:

- `README.md`, раздел **«Требования на 1 спринт»**;
- `ants.py`;
- `colony.py`;
- `storage.py`;
- `main.py`;
- задание `pra_04_tests-1.pdf`, где указано, что QA должен написать тесты и на `unittest`, и на `pytest`.

## 3. Scope тестирования

В scope Sprint 1 входят:

1. Создание колонии.
2. Создание муравьев вида «Муравьи-жнецы».
3. Проверка характеристик муравья-жнеца.
4. Симуляция одного и нескольких тиков.
5. Смерть муравья по достижении срока жизни.
6. Расход еды за тик.
7. Сериализация и десериализация колонии.
8. Локальное сохранение, список сохранений и загрузка сохраненной колонии.
9. Негативные сценарии для невалидных входных данных и поврежденных сохранений.

Вне scope текущей реализации, но важно зафиксировать как gap:

1. Пауза симуляции.
2. Запуск симуляции в реальном времени.
3. Проигрывание симуляции строго по 1 единице времени через отдельный API.
4. Генерация 2D-карты муравейника.
5. Комнаты: склад пищи, мусорка/кладбище, поверхность, королевский зал.
6. Выбор вида муравьев пользователем при создании колонии.
7. Рождение новых муравьев.
8. Ограничения по емкости склада пищи.
9. Работа с настоящей БД. Сейчас используется файловое JSON-хранилище.

## 4. Текущие допущения

Пока требования не уточнены аналитиком, QA должен использовать следующие допущения:

1. Один вызов `Colony.tick()` = одна единица времени.
2. В первом спринте реализован только вид `Harvester` / «Муравьи-жнецы».
3. Все стартовые муравьи в колонии являются рабочими.
4. Еда может стать отрицательной, потому что в коде нет ограничения на минимальное значение еды. Это нужно зафиксировать тестом как текущее поведение или как потенциальный баг.
5. Муравей считается умершим, когда `age >= life_period`.
6. После тика мертвые муравьи удаляются из списка `colony.ants`.
7. Сохранение выполняется в JSON-файл `<colony_id>.json`.
8. `load_colony("colony_1")` и `load_colony("colony_1.json")` должны загружать один и тот же файл.

## 5. Тестовые данные

| Значение | Для чего использовать | Ожидаемый результат |
|---|---|---|
| `ant_count = 0` | пустая колония | колония создается без муравьев |
| `ant_count = 1` | минимальная рабочая колония | создается 1 муравей |
| `ant_count = 15` | пример из `main.py` | создается 15 муравьев |
| `ant_count = -1` | негативный сценарий | сейчас создается 0 муравьев из-за `range(-1)`, но это нужно считать багом требований/валидации |
| `food = 0` | граница еды | после тика еда становится отрицательной при наличии муравьев |
| `food = 999` | пример из `main.py` | еда уменьшается на `2 * число_живых_муравьев` за тик |
| `life_period = 30` | проверка смерти | муравей умирает на 30-м тике |

## 6. Приоритеты

- **P0 / Critical** — без этого нельзя считать базовую модель рабочей.
- **P1 / High** — важная бизнес-логика первого спринта.
- **P2 / Medium** — негативные сценарии и устойчивость.
- **P3 / Low** — проверки удобства, структуры и будущего расширения.

```text
├── test_colony.py
└── test_storage.py
```

Но по заданию нужно показать сравнение `pytest` и `unittest`, поэтому лучше иметь отдельные файлы или хотя бы отдельные классы/блоки.

## 10. Что лучше писать на pytest

`pytest` удобнее использовать для:

1. параметризованных проверок характеристик `Harvester`;
2. граничных значений возраста: 0, 1, 29, 30, 31;
3. временных директорий через `tmp_path`;
4. проверки исключений через `pytest.raises`;
5. маркировки незакрытых требований через `pytest.mark.xfail`.

Примеры сценариев для `pytest.mark.parametrize`:

| Поле | Ожидаемое значение |
|---|---|
| `carry_capacity` | `5` |
| `life_period` | `30` |
| `food_per_tick` | `2` |
| `birth_rate` | `1.5` |
| `speed` | `1` |
| `role` | `worker` |

## 11. Что лучше писать на unittest

`unittest` удобно использовать для:

1. проверки жизненного цикла объекта через `setUp`;
2. группировки тестов по классам `TestHarvester`, `TestColony`, `TestStorage`;
3. демонстрации стандартных assert-методов: `assertEqual`, `assertTrue`, `assertFalse`, `assertRaises`;
4. сравнения с `pytest` в итоговом отчете.

## 12. Критерии приемки Sprint 1 по тестам

Sprint 1 можно считать покрытым минимально, если:

1. Есть тесты на параметры `Harvester`.
2. Есть тесты на старение и смерть муравья.
3. Есть тесты на создание колонии.
4. Есть тесты на изменение времени и еды за тик.
5. Есть тесты на удаление умерших муравьев.
6. Есть тесты на `to_dict()` / `from_dict()` для муравья и колонии.
7. Есть тесты на сохранение и загрузку JSON.
8. Есть негативные тесты на несуществующий файл и битый JSON.
9. Нереализованные требования отмечены как gaps, а не забыты.
10. Есть хотя бы один набор тестов на `pytest` и один набор на `unittest`.

## 13. Потенциальные баги и вопросы аналитику

| ID | Проблема | Почему важно | Предложение |
|---|---|---|---|
| BUG?/VAL-001 | `ant_count = -1` создает пустую колонию без ошибки | пользователь может передать некорректные данные | добавить валидацию и `ValueError` |
| BUG?/VAL-002 | `food < 0` разрешен | отрицательная еда может ломать смысл симуляции | уточнить правило и добавить валидацию |
| BUG?/SIM-001 | еда списывается на тике смерти муравья | неочевидно, ест ли муравей в момент смерти | уточнить порядок событий тика |
| BUG?/SIM-002 | нет смерти от голода | при отрицательной еде муравьи продолжают жить | уточнить механику голода |
| BUG?/SAVE-001 | неизвестный тип муравья молча игнорируется при загрузке | можно потерять данные сохранения | выбрасывать исключение для неизвестного типа |
| GAP-ROOM-001 | нет карты и комнат | требование Sprint 1 не закрыто | добавить модель муравейника |
| GAP-PAUSE-001 | нет паузы | требование Sprint 1 не закрыто | добавить контроллер симуляции или состояние paused |
| GAP-SPECIES-001 | нельзя выбрать вид при создании колонии | требование создания с видом не закрыто | добавить параметр `ant_type` / фабрику видов |

## 14. Рекомендуемый порядок написания тестов

1. Сначала написать unit-тесты на `Harvester`.
2. Затем написать unit-тесты на `Colony.tick()`.
3. Затем покрыть `to_dict()` / `from_dict()`.
4. Затем покрыть `storage.py` через `tmp_path`.
5. После этого добавить негативные тесты.
6. В конце добавить `xfail`/skip-тесты на требования, которых пока нет в коде.

## 15. Definition of Done для QA

QA-инженер завершил работу по Sprint 1, если:

1. Тесты запускаются одной командой.
2. В отчете видно, какие проверки написаны на `pytest`, а какие на `unittest`.
3. Все тесты текущей реализации проходят.
4. Все тесты на отсутствующие требования либо явно помечены как ожидаемо падающие, либо вынесены в список gaps.
5. Все найденные несоответствия зафиксированы в отчете как баги или вопросы к аналитику.
