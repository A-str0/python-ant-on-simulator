# Test Lead Brief: Sprint 4 — финал, музей боли и запрет пятого спринта

## 1. Назначение документа

Этот файл нужен тест-лиду Sprint 4. Его цель — превратить README-раздел
`Требования на 4 спринт` в понятные требования для тестировщика или другой
нейронки, которая будет писать нормальные автотесты и не спрашивать каждые
пять минут: «а матка умерла по багу или по лору?».

Документ не заменяет `README.md`. Он фиксирует, что именно проверяем, что
считаем обязательным, где можно смеяться, а где должен быть строгий `assert`.

## 2. Источники

Основной источник:

- `README.md`, раздел `Требования на 4 спринт — «Финальный Релиз, Падение Матки и Тихий Стук Бильярдного Шара»`.

Контекст предыдущего спринта:

- В Sprint 3 уже есть модель колонии, муравьи, комнаты, события, TUI, ANTCOIN,
  NPC-колонии, AI-заглушка, сохранения формата `3.0`, логирование.
- Sprint 4 не должен заново изобретать муравья. Он должен закрыть проект так,
  чтобы муравей не остался висеть между `tick()` и экзистенциальной пустотой.

## 3. Роль тест-лида

От тест-лида требуется:

1. Разобрать требования Sprint 4 на тестируемые блоки.
2. Отделить обязательный финальный функционал от декоративного щитпоста.
3. Подготовить список тестов для тестировщика.
4. Следить, чтобы тесты проверяли движок, сохранения и финальные состояния, а
   не пиксельную красоту терминала.
5. Зафиксировать риски, противоречия и допущения.
6. Проследить, чтобы в проект случайно не пролез Sprint 5 под видом хотфикса.

Кратко: тест-лид — это муравей с clipboard, который стоит у выхода из README и
говорит: «Новые требования в музей, пожалуйста».

## 4. Scope Sprint 4

В scope входят:

1. Финальная машина состояний.
2. Триггеры финала.
3. Минимум 3 концовки из 4.
4. Финальные титры.
5. Сохранения формата `4.0`.
6. Миграция сохранений из старых форматов.
7. Postgame/museum read-only режим.
8. Мемориал муравьёв.
9. Финальный экран ошибок.
10. Стабилизация: атомарные сохранения, структурные логи, таймауты AI,
    отключаемый крипторынок.
11. Регрессия Sprint 3: старая симуляция не должна умереть просто потому, что
    появился финал.
12. Тест `test_no_sprint_5`.

## 5. Out of Scope

Не тестируем как обязательную реализацию:

1. Реальный блокчейн, реальные NFT, реальные биржи.
2. Реальный OpenAI/Ollama/любой сетевой вызов в автотестах.
3. Мультиплеер, VR, мобильное приложение, редактор карт, систему модов.
4. Пиксель-перфект терминальный UI.
5. Глубокую философскую валидность последней фразы матки.
6. Спринт 5. Если он появляется, тест падает, тест-лид закрывает ноутбук,
   бильярдная играет траурный break shot.

## 6. Приоритеты

### P0 — без этого финала нет

1. Машина состояний существует и не позволяет нелегальные переходы.
2. Финал триггерится минимум по условию `1000 ticks`.
3. Есть минимум 3 рабочие концовки.
4. Любая концовка переводит игру в `CREDITS`.
5. Титры строятся из реального состояния колонии.
6. Сохранение `4.0` содержит `ending_state` и `memorial`.
7. Postgame-режим read-only.
8. Битое сохранение не удаляется.
9. AI timeout не блокирует финал.
10. `test_no_sprint_5` есть и реально проверяет README.

### P1 — должно быть, иначе релиз пахнет мокрым traceback

1. Миграция `1.0`, `2.0`, `3.0` в `4.0`.
2. God Mode не отменяет финал.
3. Бильярдная переживает любую концовку.
4. Атомарное сохранение через временный файл и rename.
5. Любое исключение в финале приводит к экрану ошибки и дампу.
6. Крипторынок отключается без сетевых запросов.
7. Структурные логи финальных событий.
8. Финальная фраза матки всегда строка, а не stacktrace, `None` или словарь боли.

### P2 — красиво, смешно, но не блокирует сдачу

1. ASCII-анимация последнего шара.
2. Залы музея по спринтам.
3. Индивидуальные строки для значимых муравьев.
4. Группировка массовки при 500+ муравьях.
5. Отдельное сообщение при отрицательном `chaos_index`.
6. Лог при загрузке после финала: пользователь сделал вид, что финала не было.
7. Кнопка `[5] Удалить смысл, но сохранить JSON` при chaos-условиях.

## 7. Тестируемые требования

### 7.1. Машина состояний

Обязательные состояния:

- `BOOTSTRAP_ANT_HELL`
- `COLONY_RUNNING`
- `PAUSED_FOR_BILLIARD`
- `CRISIS_STACK`
- `EVERYTHING_IS_FINE`
- `ENDGAME_TRIGGERED`
- `FINAL_CHOICE`
- `ENDING_ASCENSION`
- `ENDING_COLLAPSE`
- `ENDING_MUSEUM`
- `ENDING_BILLIARD`
- `CREDITS`
- `POSTGAME_MUSEUM`
- `EXIT_WITH_FEELING`

Проверить:

1. Каждое состояние существует как enum/константа/тип, а не как случайная строка
   в подвале.
2. Разрешённые переходы соответствуют README.
3. Нелегальные переходы отклоняются.
4. Из `EXIT_WITH_FEELING` нет обычного перехода назад.
5. Загрузка после финала допустима, но пишет специальный лог.

### 7.2. Триггеры финала

Минимальный P0:

1. Колония прожила `1000` тиков.

P1/P2, если разработчики успели:

1. Матка достигла `Я = 10`, `Д = 10`.
2. ANTCOIN обвалился, но бильярдная в плюсе.
3. Все соседние колонии ассимилированы или заблокировали игрока.
4. Лог событий превысил `10000` строк.
5. Пользователь нажал `F4`.
6. Последний живой муравей сидит в бильярдной `30` тиков.

Допущение: если в коде нет отдельного объекта матки, разрешается считать
«маткой» специальную запись в состоянии колонии или самого харизматичного
муравья с максимальным `Я`. Это звучит как политический кризис, но тестам нужен
детерминированный объект.

### 7.3. Финальный выбор

Экран выбора должен поддерживать варианты:

1. `ENDING_ASCENSION`
2. `ENDING_COLLAPSE`
3. `ENDING_MUSEUM`
4. `ENDING_BILLIARD`

Вариант `[5] Удалить смысл, но сохранить JSON` проверять только если реализован
режим `chaos`.

Проверить:

1. Выбор валидной концовки меняет состояние.
2. Невалидный выбор не ломает состояние.
3. Выбор концовки доступен только после `ENDGAME_TRIGGERED`/`FINAL_CHOICE`.
4. Повторный выбор после `CREDITS` невозможен или не меняет результат.

### 7.4. Концовки

#### ENDING_ASCENSION

Проверить:

1. Всем живым муравьям назначается общий `hivemind_id`.
2. Имена муравьёв не стираются.
3. Потребление еды уменьшается на 15% или сохраняется явный флаг оптимизации.
4. AI-режим становится `chorus`, если AI-модуль поддерживает режимы.
5. После концовки переход в `CREDITS`.

#### ENDING_COLLAPSE

Проверить:

1. Активные события завершаются.
2. Живые муравьи мигрируют или получают финальный статус миграции.
3. Мёртвые муравьи попадают в мемориал.
4. Бильярдная сохраняется отдельно или помечается как пережившая крах.
5. После концовки переход в `CREDITS`.

#### ENDING_MUSEUM

Проверить:

1. Postgame/museum unlocked.
2. Комнаты доступны для чтения.
3. Биографии доступны для чтения.
4. Изменяющие действия запрещены.
5. После концовки переход в `CREDITS`, затем возможен `POSTGAME_MUSEUM`.

#### ENDING_BILLIARD

Проверить:

1. Таймеры симуляции ставятся на паузу.
2. Последняя партия длится 7 тиков или фиксируется как завершённая.
3. Участники получают последние лог-сообщения.
4. Бильярдная не удаляется.
5. После партии переход в `CREDITS`.

## 8. Титры

Титры должны генерироваться из состояния, а не из воздуха.

Минимальные поля:

1. Имя колонии.
2. Количество прожитых тиков.
3. Количество рождённых муравьёв.
4. Количество умерших муравьёв.
5. Количество пропавших.
6. Самый старый муравей.
7. Последняя фраза матки.
8. Последняя ошибка, если была.
9. `chaos_index`.

Формула из README:

```text
chaos_index =
  active_events * 4
  + corrupted_officials * 7
  + billiard_games * 0.5
  + antcoin_crashes * 11
  + zombie_outbreaks * 13
  - successful_saves * 2
```

Проверить:

1. Формула считает число.
2. При `chaos_index < 0` появляется строка про подозрительно аккуратную колонию.
3. Титры не меняют состояние симуляции.
4. Если муравьёв больше 500, массовка группируется.
5. Финальная фраза матки в первом прохождении фиксированная.

## 9. Сохранения 4.0 и миграция

### 9.1. Новый формат

Сохранение `4.0` обязано содержать:

1. `version` или `save_version` со значением `4.0`.
2. `ending_state`.
3. `memorial`.
4. Данные колонии из формата `3.0`, которые нужны для загрузки.

`ending_state`:

1. `triggered: bool`
2. `ending_type: str | null`
3. `final_tick: int | null`
4. `queen_last_words: str`
5. `chaos_index: float`
6. `credits_seen: bool`
7. `postgame_unlocked: bool`

`memorial`:

1. `total_births: int`
2. `total_deaths: int`
3. `missing: int`
4. `last_ant_id: str | null`

### 9.2. Миграция

Проверить:

1. Сохранение `1.0` грузится и получает предупреждение.
2. Сохранение `2.0` получает дефолтные Б.И.Л.Ь.Я.Р.Д.
3. Сохранение `3.0` получает `ending_state` и `memorial`.
4. Битый JSON не удаляется.
5. Битый JSON переносится в `saves/museum_of_pain/`.
6. Если битый JSON содержит слово `billiard`, система пытается восстановить
   бильярдную или хотя бы пишет об этом в результат миграции.

### 9.3. Атомарность

Проверить:

1. Сохранение пишет временный файл.
2. Временный файл валидируется.
3. После валидации происходит rename.
4. При ошибке старое сохранение остаётся живым.
5. Временный мусор не считается успешным сохранением.

## 10. Postgame/Museum

В postgame разрешено:

1. Смотреть комнаты.
2. Читать биографии.
3. Экспортировать мемориал.
4. Смотреть графики.
5. Запускать последнюю партию в бильярдной без изменения статистики.

В postgame запрещено:

1. Рождать новых муравьёв.
2. Менять концовку.
3. Оживлять матку через God Mode.
4. Менять ресурсы.
5. Менять комнаты.
6. Создавать Sprint 5, даже если очень хочется.

Проверить read-only через snapshot до/после запрещённого действия.

## 11. Финальная стабилизация

Проверить:

1. Команды TUI имеют graceful fallback.
2. Случайные события логируются структурированно.
3. AI timeout заменяет текст на fallback `жил, таскал, исчез`.
4. Крипторынок может работать в offline/mock режиме.
5. Исключение в финале не выбрасывает сырой traceback пользователю.
6. При падении финала создаётся дамп.
7. Экран ошибки содержит ошибку, тик, последнюю комнату, последнего муравья.

## 12. Регрессия Sprint 3

Перед финальными тестами убедиться:

1. Колония всё ещё создаётся.
2. Муравьи всё ещё имеют Б.И.Л.Ь.Я.Р.Д.
3. Комнаты создаются и назначение муравьев работает.
4. События работают.
5. ANTCOIN майнится.
6. Соседние колонии торгуют/воюют.
7. Сохранение `3.0` можно загрузить.
8. TUI хотя бы импортируется без взрыва.

Если Sprint 4 ломает Sprint 3, это не «финал», а «вышел патч, все умерли».

## 14. Тестовые данные

### Маленькая колония

- `ant_count = 3`
- `food = 100`
- Использовать для быстрых unit-тестов.

### Колония для финала

- `time = 999`
- Один вызов `tick()` должен довести до `1000`.
- Использовать для `test_final_trigger_after_1000_ticks`.

### Колония для музея

- Есть живые и мёртвые муравьи.
- Есть несколько комнат.
- Есть биографии.
- Есть хотя бы один лог.

### Колония для collapse

- Несколько активных событий.
- Низкие ресурсы.
- Есть соседняя колония.
- Есть мёртвые муравьи.

### Битое сохранение

```json
{ "save_version": "3.0", "billiard": true, "ants": [
```

Ожидаемо: файл не удалён, перенесён в `museum_of_pain`, результат миграции
содержит предупреждение про бильярдную.

### Сохранение 3.0 без финала

Должно мигрировать в `4.0` с:

- `ending_state.triggered == False`
- `ending_state.ending_type is None`
- `memorial.total_births >= len(ants)` или другое явно задокументированное правило.

## 15. Допущения

1. Если в коде ещё нет отдельных модулей финала, тестировщик может ожидать их
   появления и писать тесты от целевого API.
2. TUI проверяется smoke-тестами и headless-режимом, если он есть. Основной
   упор — движок.
3. Все тесты с рандомом должны фиксировать seed.
4. Сетевые вызовы запрещены в автотестах.
5. AI должен мокаться.
6. Файловые тесты используют `tmp_path`.
7. Логи проверяются по структуре, а не по дословной поэзии, кроме финальной
   фразы матки.
8. Если требование явно абсурдное, тест должен проверять стабильный эффект,
   а не художественную интерпретацию. Например: «Бильярдная пережила финал» =
   комната/сущность существует после концовки.

## 16. Стратегия проверки

1. Сначала unit-тесты машины состояний.
2. Потом unit-тесты концовок.
3. Потом сохранения и миграции.
4. Потом postgame read-only.
5. Потом стабилизация и error handling.
6. Потом регрессия Sprint 3.
7. В самом конце `test_no_sprint_5`, как ритуальная печать на README.

Запускать желательно:

```bash
pytest -q
pytest --cov=src/antsim --cov-report=term-missing
```

Если coverage не дотягивает до 70%, первым делом покрывать:

1. save migration;
2. state machine;
3. endings;
4. postgame guard;
5. error fallback.

TUI в coverage не требовать. TUI и так страдает.

## 18. Риски

1. ТЗ требует финала, но код может всё ещё жить в режиме бесконечной песочницы.
2. Миграция старых сохранений может быть сложнее, чем кажется.
3. Read-only postgame легко случайно сделать read-mostly.
4. God Mode может разрушить финал, если не поставить guard.
5. AI timeout без моков сделает тесты флейки.
6. README огромный, поэтому `test_no_sprint_5` должен искать точный заголовок,
   а не любое число `5`.
7. Битые сохранения нельзя удалять, иначе тесты станут археологами без экспонатов.
8. Бильярдная должна пережить финал. Это не риск, это закон природы.

## 19. Definition of Done для тест-лида

Работа тест-лида Sprint 4 считается выполненной, если:

1. Есть этот документ.
2. Есть список P0/P1/P2 требований.
3. Есть минимальный набор имён тестов.
4. Есть понятные тестовые данные.
5. Есть правила для моков, файловой системы и AI.
6. Есть критерии, когда функционал считать готовым.
7. Есть запрет на Sprint 5.
8. Другой человек или нейронка может открыть этот файл и написать тесты без
   обряда вызова аналитика через феромоновую доску.

Финал может быть с бильярдом.
